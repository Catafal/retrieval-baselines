The spec, in one line

Add the dense arm to Experiment 003's scored run — same pool, same 7,405 queries, same GRAPH_MEASURES — so the instalment delivers three families rather than two.

Design decisions (spec was ambiguous → here's the call I made)

Decision Write and tag an amendment before computing a single vector. Checking the protocol first turned up the thing that decided the whole shape of this task: protocol-003 pins no encoder and never registers dense as an arm. §3 says "every arm is scored against this identical candidate set" and names none. So adding dense is an addition after the tag, not the execution of something already registered. It is now protocols/003-amendment-2-dense-arm.md, tagged protocol-003-amendment-2, committed before any embedding existed. Had I simply run it, the entry would have reported a number that no pre-registration covered, which is the failure the retraction was about.
Decision Both encoders, not one. 002's central finding is that swapping MiniLM for BGE flipped SciFact's corpus-level verdict while the per-query gradient survived. An entry whose lesson is "corpus-level verdicts are encoder-dependent" cannot then report one encoder and call it "the dense arm" — that is the exact error 002 exists to warn against. Both are affordable only because the pool is 66,581 passages rather than 5,233,329, which is precisely why 002 amendment 2 excluded HotpotQA from its own BGE run.
Decision Dense is excluded from the registered Holm family, in writing. §7's clauses A and B are already resolved, with p-values corrected across a family declared before the run. Adding members now would change the correction applied to settled claims — retrospective re-scoring of a result that has already landed. The amendment prohibits it explicitly rather than leaving it to judgement, and any per-class dense figure is labelled exploratory.

Deviations (intentional departures)

Deviation Amendment 1 is untagged; amendment 2 is tagged. Inconsistent on its face, deliberate underneath. Amendment 1 records a prediction that failed after the fact — there is nothing to freeze, and tagging it would imply it constrains future work. Amendment 2 registers work not yet done, so freezing it is the entire point. The rule I applied: tag what constrains the future, commit what documents the past.

Tradeoffs (alternatives considered)

Tradeoff Reuse 002's encoder factory vs. re-declare the pins in the 003 runner. Re-declaring would have been a three-line change and self-contained. Rejected: two copies of a pin is one copy too many. The whole purpose of pinning is that the artefact cannot drift, and a second declaration is exactly how it drifts — the two would agree today and diverge the first time either is edited. The 003 runner imports _make_encoder and ENCODER_CONFIGS from 002 instead, so there remains one place where a model name and revision are written down.
Tradeoff Run the two encoders in parallel or in sequence? Sequential, though parallel would roughly halve wall-clock. The protocol requires build cost and query cost reported separately, and two CPU-bound encoders competing for the same cores produce timings that describe the contention rather than the arm. A number reported as cost should be a cost.
