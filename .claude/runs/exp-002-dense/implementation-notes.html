The spec, in one line

Make protocols/002-amendment-1-dense.md's dense and hybrid arms real: a working, cached, controlled dense retriever wired into the ladder runner, the four pre-registered query properties, per-query win/loss analysis, and paired-bootstrap statistics — run once, end to end, on SciFact.

Design decisions (spec was ambiguous → here's the call I made)

Decision Embedding cache is content-addressed, not dataset-named. The amendment says "cached to disk per corpus... keyed by model revision." Rather than have DenseRetriever know a dataset name (it only ever sees a corpus dict), the cache key is a SHA-256 over (max_length, sorted doc_ids, doc texts), stored under a directory named for the encoder's revision. Two independent guarantees fall out of this: a different revision physically cannot land in another revision's directory, and a corpus whose content changed (even with identical ids) cannot silently reuse stale vectors.
Decision batch_size moved from DenseRetriever to the encoder. The task brief named this exactly: "an earlier review found batch_size reported but never reaching the encoder." Confirmed — DenseRetriever.__init__ took a batch_size parameter, put it in the manifest, and never passed it anywhere; SentenceTransformerEncoder.encode_documents referenced self.batch_size, which the encoder never set (would have raised AttributeError the first time it ran). Fixed by making the encoder the sole owner of batch_size — it is the only object that calls .encode() — and DenseRetriever.manifest() now reads it back from self.encoder.batch_size. A regression test (test_manifest_reports_batch_size_from_the_encoder_not_a_separate_field) pins this.
Decision max_length verified against the loaded model, not hard-coded. Loaded the pinned revision directly and read model.max_seq_length: it is 256, matching the amendment (the ladder pre-registration's original 512 is superseded by the amendment, which the amendment itself says: "That gate is now closed here"). Pooling mode (mean) and the presence of a built-in L2-normalisation module were read the same way — SentenceTransformerEncoder no longer hard-codes pooling = "mean" as a class attribute; it inspects the loaded model's modules. All three actual values, plus what was requested, are recorded in encoder.verification and folded into the manifest.
Decision doc_ids sorted, not list(corpus). The pre-existing DenseRetriever.retrieve() used doc_ids = list(corpus), trusting dict insertion order — a house-rule violation ("no dict-order dependence") and the reason the embedding cache could not be keyed reliably: the same corpus dict built via a different code path could fingerprint differently. Changed to sorted(corpus), matching lexical.build_index's own convention.

Deviations (intentional departures from the spec/convention)

Deviation Cross-process determinism checked as a subprocess unit test plus a manual empirical rerun, not as a runtime gate inside run_dense/run_hybrid. The amendment lists it as a control that halts the run. Implementing it as an in-process gate would mean re-embedding SciFact in a second subprocess on every invocation, doubling the cost of every rerun for a property that (a) does not depend on the embedding step at all — the dense/hybrid ranking code has no set-iteration or hash-order dependency, unlike the BM25 bug this repo already hit — and (b) is adequately covered by a fast subprocess test against a stub encoder plus one manual empirical check against the real model (results/002/scifact/{dense,hybrid}/per_query.jsonl diffed byte-for-byte across two separate python -m rb.experiments.ladder.run invocations — both diffs are empty). Flagging for review: if a reviewer wants this as an automatic per-run gate rather than a test-suite property, that is a small addition (rerun the retriever in a subprocess and diff) but it would double dense/hybrid wall clock on every future invocation.
Deviation Self-retrieval control samples 100 documents, not the whole corpus. The amendment states the control's requirement ("a document... must retrieve itself at rank 1") but not a sample size. Re-encoding every one of SciFact's 5,183 documents as a query would roughly double the dense rung's wall clock for a control whose failure mode (query/document encoder transposition) is not corpus-size-dependent — if it fails, it fails for essentially every document, so a sample catches it. 100 is deterministic (sorted doc ids, first 100), not random.

Tradeoffs (alternatives considered)

Tradeoff Win/loss bin edges: equal-count quantiles vs. equal-width ranges. Considered equal-width bins (fixed-size ranges of the raw property value). Rejected: IDF and Jaccard overlap are both skewed on SciFact, and equal-width bins would put most queries in one bin and leave the others sparse by construction, which is a worse failure mode than the sparse-bin flag is meant to catch. Went with equal-COUNT quantile bins (rank-based split into four groups) instead, so every bin (for a continuous property) has a comparable number of queries and the win-rate interval is comparably powered across bins. gold_count is the exception — binned by exact integer value, since quantile-splitting an already-discrete variable would arbitrarily fracture "2 gold docs" across two ranges.
Tradeoff Win/loss interval: reuse paired_bootstrap per bin vs. build a new win-rate-specific bootstrap. The amendment asks for "win rate... with intervals, alongside the paired per-query difference." Rather than invent a new statistic, each bin's report is exactly one call to the already-tested rb.stats.paired_bootstrap on the bin's subset of per-query differences — this gives the interval on the mean difference (which implies the sign/strength of the win) using code this repo already trusts, instead of a second, parallel bootstrap implementation for proportions that would need its own tests and its own scrutiny.

Open questions (want your confirm/revise)

Open Is SPARSE_THRESHOLD = 5 the right cutoff? Not pre-registered by the amendment (which fixes the four properties, not a bin-size cutoff). Chose 5 as a documented, conservative floor — analysis.SPARSE_THRESHOLD. On SciFact's 300 queries this only bites the three sparsest gold_count bins (2, 3, and 5 gold docs — 4, 3, and 2 queries respectively), which is exactly the multi-hop tail where sparsity should be flagged. Changing it is a one-line edit if a different threshold is wanted.
Open Hybrid beat full BM25 by 0.022 nDCG (not Holm-significant, p=0.052) — report as "no" or as "borderline"? The pre-registered stopping rule (protocol-002-ladder.md section 8, amendment section 10) says publish whatever comes out and call a non-significant result what it is. Reported here as holm_significant: false, which is correct per the protocol, but 0.052 is close enough to the 0.05 line that a reader skimming only the boolean might miss how close it was — the full mean_diff/ci95/p_value are in the artifact for exactly this reason. No code change needed either way; flagging so the write-up doesn't round "borderline" down to "no effect."
