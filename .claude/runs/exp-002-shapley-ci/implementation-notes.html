The spec, in one line

Put a query-resampled bootstrap interval and pairwise ordering fractions on the Shapley attribution already measured for lexical/002, add a (not-yet-wired) Spearman rank correlation and a corpus length-statistics function for later use, and regenerate the three existing lexical_factorial.json artifacts from their committed per-query artifacts — without re-running retrieval and without changing the existing exact Shapley point values. The full notebook spec (NB-13/14/15) also covers a pre-registered out-of-sample corpus extension (Job 2); this task explicitly descopes that to infrastructure-only (Spearman stat, length stats) and forbids touching the dataset allowlist.

Design decisions (spec was ambiguous → here's the call I made)

Decision Bootstrap function signature: shapley_bootstrap(per_cell_scores, players, rounds, seed). per_cell_scores maps each of the 8 subset-frozensets to a query-aligned list of per-query nDCG@10 (same convention shapley_values already uses for its value function, just query-level instead of scalar). Iteration over cells is sorted by tuple(sorted(subset)) rather than dict insertion order, so behaviour cannot depend on caller construction order (house rule: no dict-order dependence).
Decision Point estimate stays the existing exact Shapley value; the bootstrap only adds ci95 and pairwise ordering. The spec's Job 1 already has an exact Shapley computation from the full data (shapley_from_ndcg/shapley_values). The bootstrap's per-round Shapley values are only used to build the percentile interval and the ordering fractions, not to replace the point estimate — this is also what keeps the "point values must come out identical" regeneration check meaningful: the point values never touch the new bootstrap code path.
Decision Length stats function lives in lexical.py, not stats.py. It must use the same tokenizer the lexical scorer uses (_tokenize), which is private to lexical.py. Putting a dataset/domain-specific function in the generic stats.py module (shared across future experiments per its own docstring) would import a lexical-specific tokenizer into a module that's supposed to stay generic. stats.py keeps the two genuinely generic additions (Shapley bootstrap, Spearman); corpus_length_stats sits next to _tokenize in lexical.py instead.
Decision Regeneration is a new CLI rung, --rung shapley-intervals, calling add_shapley_intervals(dataset) in run.py. Reuses _load_subsampled, _per_query_ndcg and ALL_CONFIGS already in that module rather than a one-off script, and is testable the same way run_lexical_factorial already is (monkeypatch RESULTS to tmp_path). It reads each config's already-committed per_query.jsonl, recomputes per-query nDCG, checks the recomputed per-cell means against the numbers already stored in configs (see Deviations — this is the "must come out IDENTICAL" check the task description asks for), then adds shapley_ci95 and shapley_pairwise_ordering to the existing JSON in place. It does not call retrieve(), build_index(), or the closure control again.

Deviations (intentional departures from the spec/convention)

Deviation Length stats are NOT wired into lexical_factorial.json. Item 3 of the task ("wire both into the factorial run") names only the bootstrap interval and pairwise ordering fractions ("both" = items 1 and 2). Item 5 (length stats) is asked for as a standalone, tested function, matching the treatment of item 4 (Spearman — built and tested, explicitly "do not use it yet"). Keeping length stats out of the regenerated JSON keeps this run's write surface to exactly what item 3 named, per the "nothing more than the six items" house rule. It is trivial to wire in later (one line in add_shapley_intervals) once Job 2 needs it as a per-corpus artifact.

Tradeoffs (alternatives considered)

Tradeoff Where to put the "same query draw across all 8 cells" guarantee. Considered exposing a shared_draws: bool toggle on shapley_bootstrap so the pairing test could call the same function both ways. Rejected: the spec calls breaking the pairing "the single most important property... it must have a test that fails if it is broken" — a toggle makes the wrong behaviour reachable in production code, which is exactly the failure mode being guarded against. Instead the pairing test builds its own small "broken" independent-draw bootstrap inline, in the test file only, and asserts the real function's intervals are narrower.

Open — BLOCKING The three committed lexical_factorial.json files were NOT regenerated. The "must come out identical" check caught a real, pre-existing precision gap in _per_query_ndcg.

add_shapley_intervals's consistency check — recompute each cell's mean nDCG@10 from the committed per_query.jsonl and compare against the committed point value — failed. Root cause, confirmed by direct experiment (live retrieve() + pytrec_eval vs. the per_query.jsonl reconstruction, on real data, read-only, nothing written): pytrec_eval appears to compare scores at reduced (roughly float32) precision internally. Two documents whose real BM25 scores differ only by the 1e-9-per-rank tie-break epsilon LexicalRetriever applies are, to pytrec_eval, exactly tied — and it resolves that tie with its own convention (order-independent, and not always in the same direction: sometimes higher, sometimes lower than our reconstruction). _per_query_ndcg's reconstruction assigns each document a synthetic score far enough apart that no such tie exists, so it evaluates strictly by the recorded rank order — which is what the original live run's pytrec_eval call did NOT do whenever the real scores were this close together.

Measured scope (recomputed mean nDCG@10 per cell vs. the committed value, both rounded to 4 decimals to match run_rung's own rounding):

CorpusCells affectedLargest diffLikely reason
SciFact2 of 8 (both idf=False)0.0021occasional raw-tf ties
HotpotQA4 of 80.0006occasional ties, large corpus dilutes them
Quora8 of 8 (every cell)0.0039mean doc length ~11.7 tokens — short documents make raw-score ties common

This is a pre-existing property of _per_query_ndcg, used unchanged by the already-committed adjacent_rung_comparisons section (specifically the lexical(none) rung, LADDER's first element) — not a defect introduced on this branch. It was never visible before because nothing previously cross-checked a reconstructed value against a live-computed one at 4-decimal precision. Ironically it hits hardest on Quora, the corpus central to the length hypothesis this whole experiment is building toward.

What I did instead of forcing it through: left all three committed JSON files untouched, and did not write shapley_ci95/shapley_pairwise_ordering to disk anywhere. I computed the bootstrap and ordering fractions anyway, in memory only, using the same (slightly imprecise on some queries) reconstructed data add_shapley_intervals would use, to show what the numbers look like — see the final report for the actual figures. The magnitude of the imprecision (≤0.004 in a point estimate) is small relative to the ~0.05–0.10 interval widths already measured, so it is very unlikely to flip any qualitative conclusion, but "very unlikely" is not "verified," which is exactly the standard this task's own consistency check is holding everything else to.

Options for a reviewer: (a) accept a documented, bounded tolerance (e.g. 0.005) on this check with the root cause on record, and let me regenerate; (b) fix _per_query_ndcg to replicate pytrec_eval's tie convention exactly (nontrivial — its convention isn't obviously order-independent-of-magnitude, it needs reverse-engineering or an upstream source read); (c) regenerate by re-scoring from the live retriever instead of the artifact (defeats the "costs seconds, not 45 minutes" reason this job exists, though SciFact/Quora are cheap — only HotpotQA is expensive). I did not pick one unilaterally because the task's own instruction was explicit: stop and report on any change, not decide for the author.
