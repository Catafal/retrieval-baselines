The spec, in one line

Make bm25_closure able to fail without making it flaky, and route all four percentile call sites through the derived _percentile_index helper with proof that no committed number moves. Both mutation-verified.

Design decisions (spec was ambiguous → here's the call I made)

Decision Tolerance set to 0.05, chosen by measuring defect effect sizes rather than by taste. The spec said not to pick 0.03 just because it was suggested, so I measured what defects actually cost in nDCG@10 and set the gate between the largest legitimate difference and the smallest defect the control can see.

Measured on SciFact and Quora with the committed scorer. The old 0.10 caught the two wrong-formula defects at only a 1.08× margin — it barely cleared the largest defect that exists. 0.05 doubles that margin while keeping 1.8× headroom over the largest legitimate delta.
Decision The control now states what it cannot catch, in its own docstring and in the artifact. A control whose limits are undocumented invites the reader to assume it covers everything. The docstring now names the two invisible classes and points at where they ARE covered (tests/test_bm25_constants_pinned.py for k1/b, the factorial equivalence tests for the switches).

Deviations (intentional departures from the spec/convention)

Deviation Tightening the tolerance does NOT achieve the spec's stated goal, and I am saying so rather than implying it does. The spec's premise was that at 0.10 the control "would only catch a catastrophically broken tokenizer, not a subtle scoring defect". The measurement says that is true at every safe tolerance: a k1 drift moves nDCG by up to 0.0211 and the legitimate difference to published is already 0.0272, so no threshold separates them. The subtle-defect class is below this control's resolution by construction, not because the number was too loose. 0.05 is still worth doing — it doubles the margin on the defects the control can see — but it buys a better gate, not a new capability.

Tradeoffs (alternatives considered)

Tradeoff 0.05 flat vs. 0.03 flat vs. per-corpus tolerances. 0.03 clears HotpotQA's 0.0272 by only 0.0028 — one corpus revision or a BEIR re-release and it false-fails on correct code, which is how a control gets quietly loosened until it means nothing. Per-corpus tolerances fit tighter but are a free parameter per corpus, which is exactly the shape of a gate tuned until it passes. Flat 0.05 is one number, defensible from the measurement, and it fails loudly if a future corpus disagrees by more — which is a question worth being asked.

Deviations, continued

Deviation A mutation-sweep methodology defect was found mid-run, and it is not specific to this work. While mutation-verifying the tolerance, the imported BM25_CLOSURE_TOLERANCE was 0.03 while the source file said 0.05. Cause: restoring a mutated file with cp sets its mtime to now, and the __pycache__ .pyc had been written in the same second. Python invalidates bytecode on mtime plus size — the two candidate values are the same length — so the restore was invisible and a stale .pyc kept serving the mutated constant.

Why this is worth more than the fix. Every mutation sweep in this project uses write-then-cp-restore. A stale .pyc means the mutation is never loaded, the tests pass, and the sweep reports SURVIVED — a false hole, in the exact direction that wastes effort rather than hides a bug. Kills stay trustworthy: a test can only fail if the mutated code actually ran.

The four survivors from the 002 sweep were each independently re-demonstrated afterwards (arm swap via a real artifact regeneration in a fresh subprocess; the two percentile siblings and k1/b by watching the new tests fail), so no conclusion in that review rests on this. But any future sweep must run with PYTHONDONTWRITEBYTECODE=1 or clear __pycache__ between mutations.
