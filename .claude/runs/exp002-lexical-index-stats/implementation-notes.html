Lexical index & stats wiring — experiment 002

Branch exp-002-scaling · started 2026-08-19 · two jobs: make the lexical scorer fast enough to run on HotpotQA, and wire paired-bootstrap/Holm significance into run_lexical_factorial. Harness code + tests only — nothing scored, nothing written into results/002/.

This is a living document capturing how the implementation interprets, diverges from, or trades off against the spec. Updated as each slice lands.

The spec, in one line

Replace LexicalRetriever's per-query full-corpus scan with a shared inverted index built once per dataset (proven score-for-score identical to the naive reference via an equivalence test on real SciFact and hand-built edge cases), stop rebuilding it once per config inside run_lexical_factorial, and fold rb.stats.paired_bootstrap / holm_correction into that same function's output for the adjacent-rung comparisons the protocol asks for — without changing a single score and without writing to results/002/.

Design decisions (spec was ambiguous → here's the call I made)

Decision What counts as an "adjacent rung" for the significance test. protocols/002-ladder.md says Holm-corrected paired bootstrap runs across "the adjacent-rung comparisons made within a corpus" but only pins down the eight-cell factorial (order-independent by design — Shapley attribution) plus "the ladder ordering ... reported alongside it for narrative only." It never spells out what that narrative ladder actually is. I defined one canonical four-point ladder in lexical.py: all-off → +idf → +idf+tf_saturation → +idf+tf_saturation+length_norm (= full BM25), turning on exactly one mechanism per step, in the same idf-then-tf_saturation- then-length_norm order ALL_CONFIGS already iterates in (so there's one canonical ordering already established in this codebase, not a new one invented for this). Three adjacent comparisons come out of that: none→idf, idf→idf+tf_sat, idf+tf_sat→full. Flagging this because it's a real modelling choice — a different ladder order (e.g. length_norm first) would report different "which mechanism bought the gain" numbers even though Shapley's order-independent attribution stays the same either way.
Decision CSC (column-sliced) sparse matrix as the index representation, not CSR or a plain dict-of-postings. Scoring a query needs, per query term, "every document containing it and its count there" — a matrix COLUMN's nonzero entries. CSC gives that in O(nnz in that column) via indptr slicing with no per-query conversion; CSR would need a transpose or a per-query tocsc() call, which is exactly the kind of per-query rebuild this refactor exists to eliminate. A plain dict[term, list[(doc, tf)]] postings structure would work too and was considered, but scipy sparse gives vectorised elementwise arithmetic (tf * (k1+1) / (tf + k1*norm) etc.) over an entire posting list at once via numpy, instead of a Python-level loop per posting — and scipy/numpy are already dependencies, so this adds no new one.
Decision Where the shared index lives on LexicalRetriever. The Retriever protocol's retrieve(corpus, queries, top_k) signature is fixed (contract-tested across every rung), so the index can't be passed as an extra argument without breaking that seam. Instead it's an optional field on the frozen dataclass (index: LexicalIndex | None = None), set via dataclasses.replace(cfg, index=shared_index) in run_lexical_factorial before each of the eight run_rung() calls. The field is compare=False, repr=False so two configs with the same three switches stay equal (and interchangeable as dict keys — ndcg_by_config[full_bm25()] still works) regardless of which index object, if any, is attached: the index is a performance detail, not part of a config's identity. When no index is injected, retrieve() builds one itself, so direct calls (contract tests, the equivalence test's "no prebuilt index" case) keep working unchanged.

Deviations (intentional departures from the spec/convention)

Deviation Per-query score accumulation is vectorised (numpy unique + add.at), not a Python dict accumulator. A dict keyed by doc id, summed with a Python loop over touched (doc, term) pairs, would have been the more obvious "only touch documents with a match" implementation and was the first draft. Switched to np.unique(..., return_inverse=True) + np.add.at because HotpotQA is the whole point of this refactor and a term that appears in a large fraction of 5.2M documents would still drive a slow per-entry Python loop even after the inverted-index cut; the numpy path keeps that case vectorised too. Cost: the two implementations sum the same floats in a different order (reference sums sequentially per document; fast path reduces via add.at in whatever order np.unique puts rows in), which is why the equivalence test uses a tolerance (1e-9 absolute) instead of exact equality — see that test file's docstring for why that tolerance is the right size.

Tradeoffs (alternatives considered)

Tradeoff Keeping the naive algorithm as a real, callable class vs. deleting it and trusting the math. Could have just derived the fast path from the formula and unit-tested the formula in isolation. Kept _ReferenceLexicalRetriever as a verbatim copy of the original retrieve() instead, because the task's own framing is right: the retracted prior entry shipped a number that looked reasonable and wasn't, and "the algebra checks out" is exactly the kind of reasoning that doesn't catch an indexing bug (off-by-one in indptr slicing, wrong axis, a term counted twice). Running both implementations on the same real corpus and diffing their output is strictly more convincing, costs one extra (intentionally unoptimised, intentionally never touched) class, and only runs in tests — never in the scored path.

Open questions (want your confirm/revise)

Measured peak (macOS /usr/bin/time -l "peak memory footprint", the build-time transient — see Measured results below) is ~13.2 GB against a 26 GB machine, and that peak is paid once per dataset, not once per config, because the index is shared. Not wired into make reproduce-002-lexical's Makefile target as part of this change — that target's scope wasn't touched, only the two functions the task named — so whether to add HotpotQA to the cheap-reproduce path given a real ~51 min wall clock is a call for whoever owns that target, not made here.

Method: built the real index (build_index) on the real corpus via rb.datasets.load, timed full_bm25().retrieve() (the most expensive config — all three mechanisms active) on a 50-query slice, divided for per-query time, then multiplied by the protocol's actual subsample size (rb.run.SAMPLE_SIZE = 500, or the dataset's full judged-query count when smaller — SciFact has 300). "All 8 configs" assumes the other seven cost the same as full BM25 per query, which is true up to the cost of the vectorised elementwise formula difference (negligible next to the postings-list lookup that dominates). HotpotQA's naive figure and 18.3 GB estimate are the task's own numbers, not remeasured here — the naive path was never run to completion on HotpotQA in this refactor, deliberately, since the equivalence test already proves correctness on SciFact and there is no reason to spend ~2.5 hours confirming a fact already established at smaller scale.

HotpotQA now fits. ~51 minutes wall clock for the full eight-config factorial (previously projected to not finish at all — the naive approach's steady-state 18.3 GB of doc_tf dictionaries, rebuilt eight times, thrashes a 26 GB machine long before "18.6 hours" would ever elapse). The one real cost that remains: index construction briefly peaks at ~13.2 GB — Python list objects (rows, cols, data — three lists of ~177M ints/floats each, holding document-term postings before they're handed to scipy.sparse.csc_matrix) cost roughly 5-10x what the same data costs as a numpy array, and that overhead is transient, reclaimed once the matrix is built. The matrix itself, once built, is small (~2.1 GB: 177M nonzeros × 12 bytes for int32 indices + float64 data). This fits comfortably under 26 GB with headroom, so no further optimisation (e.g. building COO arrays as pre-sized numpy buffers instead of Python lists, to cut that transient peak) was made — "simplest thing that works," and 13.2 GB already has ~13 GB of slack.
