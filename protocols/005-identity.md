# Protocol 005 — Stage 0: identity, and what it covers

**Status: frozen on tagging as `protocol-005-identity`.** Written and committed before the first
request is sent to any Wikipedia endpoint and before any registry exists. No retrieval number is
produced by this stage, and none may be.

This protocol freezes **how identity is constructed**. It does not register a prediction. The
prediction, its falsifiers and the scored 2x2 belong to `protocol-005`, tagged after the coverage
this stage measures is known and reported.

## 1. Why this stage exists separately

004 registered an oracle ceiling of 0.3344 in advance, as an upper bound nothing could beat: the
corpus titles used as entities, a perfect linker over a fixed entity set. GLM-4.7-Flash returned
0.3699.

Beating a registered ceiling normally means a defect. This one did not. The oracle bounded **one
definition of what an entity is**, not extraction in general, and a better extractor found
entities that definition never contained. The correction is the finding: this arm's performance
lives in its **node set**, not in its walk.

003 and 004 both key entities by exact normalised string. "Cleveland State" and "Cleveland State
University" are two nodes with no edge between them, and no walk can cross what the node set did
not join. 005 holds personalized PageRank fixed and changes only what it walks over.

Identity is the one component of 005 that is not already built and published, and the only one
that can fail outright. So it is built and measured first, under its own tag.

## 2. The hazard this tag exists to prevent

The merge policy has real degrees of freedom: case folding, whether an alias that is itself an
article is kept, what happens when one alias points at two documents. Every one of them moves
coverage.

Choosing those rules **after** seeing coverage is tuning the input to the outcome. NB-23 already
forbids a hand-authored alias registry for that exact reason; a policy selected against a measured
coverage number is the same failure in a less visible form.

Section 4 is therefore frozen here, before the first request. Coverage is measured afterwards and
reported whatever it says.

This is the pilot-then-full split 004 used, applied to the component that carries the risk.

## 3. The identity source

**Wikipedia redirects, scoped to the pool titles of each corpus.**

Both corpora are Wikipedia-derived and their document titles are exact article titles. Redirects
are an alias registry that already exists, was authored for reasons unrelated to this experiment,
and cannot be tuned by it. That last property is why they are the candidate and a hand-authored
file is not.

**Scope.** Only redirects whose target is a title in the experiment's pool are fetched — at most
the 66,581 HotpotQA and 43,487 2Wiki pool passages' titles. Batched at the API's 50-title limit
this is on the order of 2,200 requests. The full `redirect` and `page` SQL dumps are not used: the
join they would require buys nothing over a scoped fetch and adds multi-gigabyte inputs no reader
would download to check a number.

**Reproducibility.** The live API is mutable, so it is not the artifact of record. The fetched
registry is committed together with a manifest recording endpoint, fetch date, request count and
sha256, and every downstream command replays from the committed snapshot with no network access.
This is the precedent 004 set for its extraction cache, adopted here for the same reason: when the
source is not deterministic, the artifact is what a reader re-runs against.

## 4. Construction rules

Frozen before the first request. Each is mechanical, and none is selected by inspecting a result.

- **R1 — scope.** A redirect is kept only if its target is a pool title. Built per corpus,
  separately, with no sharing between them.
- **R2 — namespace.** Main namespace only.
- **R3 — key.** `normalise(alias_title)`, reusing the existing function unchanged.
- **R4 — value.** `normalise(canonical_title)`.
- **R5 — self-collision.** An alias that is itself a distinct pool title is dropped. Merging it
  would erase a document's own identity. The count is reported.
- **R6 — ambiguity.** An alias resolving to more than one canonical within the corpus is dropped.
  The count is reported. This is the registered guard against the precision failure NB-23 names in
  advance: merging entities that share a name creates paths that do not exist.
- **R7 — no hand editing.** One committed command generates the file. No additions, no removals,
  no per-corpus exceptions. A registry that cannot be regenerated by that command is not this
  registry.
- **R8 — no language filter.** Foreign-script redirects are kept. They cannot match English
  extracted entities, so they cost nothing, and removing them would be a judgement capable of
  being tuned.

R3 has a consequence worth stating: typed identity is a **strict superset** of the current string
matching. Anything that matched before still matches. An empty registry reproduces 003 and 004
exactly.

## 5. The seam

Identity resolution is one function today, called from exactly two places: `build.build()` when
the graph is constructed, and `GraphRetriever._seed()` when the query is linked into it.

It becomes an **injected linker**, on the principle 004 established for the extractor and for the
reason NB-23 states: **both sides or neither.** A graph built under one identity and seeded under
another is not an experiment, and supplying one without the other raises rather than silently
mismatching.

The default resolves at call time, not at construction. 004 found that binding at construction
defeats injection, and the suite carries a regression for it.

    link(raw) = registry.get(normalise(raw), normalise(raw))

With an empty registry this is byte-identical to today's behaviour. The string arm and the typed
arm are therefore the same code path with different data, which is what makes the comparison an
experiment rather than two programs.

## 6. What is measured, and reported before any retrieval number

Written to `results/005/identity-coverage.json`, for each corpus and each extractor. Both
extractors replay from committed caches: spaCy is deterministic and local, and the GLM cache is
the 144,528-key artifact 004 committed. **This stage spends nothing and calls no model.**

- **C1** share of graph nodes resolving through an alias
- **C2** node-set size, before and after
- **C3** share of query entities resolving through an alias
- **C4** merge-size distribution across canonicals actually hit
- **C5** the **alias-affected query subset**: queries with at least one entity resolving through an
  alias
- **C6** the R5 and R6 drop counts

C5 is fixed here, before any score exists, because it is the population the mechanism claim is
decomposed over in Stage 1. A subset chosen after seeing which queries improved would confirm
anything.

**The floor is a minimum detectable effect, not a threshold.** No coverage percentage is declared
sufficient in advance. Instead the MDE for the concentration comparison is computed at the
observed C5 size, by the same two-proportion estimator 004 used to size its query-extraction gate:
80% power, alpha 0.05 two-sided. If that subset cannot detect an effect the size 004 produced, the
mechanism is untestable on these corpora and the experiment reports that it could not have found
an effect, rather than that it found none.

That estimator, and the Wilson interval beside it, are currently private helpers inside
`reasoning_ablation.py` — one entry's producer, not shared machinery. Stage 0 moves both into
`stats.py` unchanged, with the tests they never had, so 004 and 005 quote one implementation
rather than two copies. The move is behaviour-preserving and is verified by recomputing 004's
committed `reasoning-ablation.json` from the promoted functions and requiring it to be
byte-identical. If it is not, the move is wrong and is reverted rather than accepted.

A threshold invites renegotiation once the number lands. An MDE cannot be renegotiated, because it
is a property of the sample size and is computed the same way whatever the answer.

## 7. The outcome this stage is allowed to have

**Low coverage is a result, not a failure.** If redirects do not reach the entity forms that
matter, the finding is that typed identity works where identity is curated, and that curation is
the cost nobody prices. It ships, under BRAND.md prohibition 1, exactly as a positive result
would.

The one outcome not permitted is discovering low coverage and then adjusting section 4 to raise
it.

## 8. Not in this stage

No retrieval run. No R@2. No BM25 or dense comparison. No Holm family. No registered prediction.
No entry drafted. No change to any published 003 or 004 number.
